# 战报数据库、查询与验收

日常双击桌面“战报采集.cmd”打开图形界面，再点击“开始采集”。底层主流程仍为“逐页完整优先采集 → 原文归档与入库 → 独立中文语义辅助表”。中文映射失败不会回滚已保存的原文，HTML 展示仍是可选工具。需要原命令行时给启动器加 `-Console` 或 `-Once`。

## 省空间模式

`collect` 默认使用 `--storage-mode lean`；`import` 默认 `full`，可显式选择。`compact` 保留完整原件、组件、事件和现有业务查询需要的元数据，仅跳过 `/data/eventDataList` 和组件内对应事件数组的后代字段索引；数组本身仍保留容器节点。`lean` 在此基础上另跳过 `/components/snapshots` 与 `/components/statics` 的后代索引，保留组件根节点，完整内容仍在 `report_components.payload_json`。未知分支中同名字段不受影响。事件的顺序和原始参数在 `report_events` 中完整保存。完整性判定仍检查原文全部节点，包括未索引组件中的序列化异常。

每个快照有独立的 `storage_mode` 和 `indexed_field_count`，`field_count` 继续记录完整原文节点数。未标记模式的旧快照按 `full` 解释，写入时只增加兼容列，不转换旧数据；只读访问旧库不修改结构。自动采集对 compact/lean 快照只持久化 ID 名称映射，事件中文解释由 GUI 详情及 CLI `explain` 按当前页只读生成并注明实际字典版本，不写回数据库。手动 `enrich` 允许补建持久解释。对未取得的事件、未知值和异常仍保持原有提示，不能因省空间改变五组件完整度。

lean 名称映射仍从完整原文选取所有 compact 模式下的 ID 路径，包含武将快照及统计组件内的路径；相同完整来源与映射按 SHA-256 共享存入 `report_semantic_mapping_cache`，`report_semantic_id_links` 保留明确关联，名称行的两个大 JSON 列改存引用。`report_resolved_id_meanings` 视图展开完整来源；Python `resolve_id_meaning` 还核对哈希与关联。full/compact 的这两个 JSON 列维持原格式，原有名称、ID 和路径查询不变。

新生成的战报 JSON 使用紧凑排版，已存在原件仍按原字节归档和 SHA-256 校验。此变更减少新增数据体积，不会删除旧采集目录、备份或历史版本；已经运行的旧采集进程需正常停止后重新开始才能使用新代码。


## 图形界面与后台采集

打开界面只读取本地档案与状态，不自动连接游戏。开始按钮启动现有采集入口，继续使用已有数据库与检查点；停止按钮发送正常停止信号，让采集器保存数据并清理连接。已有同数据库采集器时，界面显示其状态并阻止重复启动。

总览新增“上一封采集用时”：正式 `capture_started` 到本封入库及最终状态保存完成后由 `capture_finished` 发布单调时钟耗时，CLI写入 `collector_status.json.last_capture` 并记录诊断事件。值包含账号、战报ID、秒数、结束时间和complete/partial/failed结果，下一封开始不覆盖旧值；失败保留具体错误与重连标志，元数据更新、纯本地待导入恢复和跳过不产生新计时。计时不进入战报payload或归档版本。旧进程兼容读取同PID/创建时间/账号/周期的有限日志尾部，近似值标“约”，不把中间partial片段当成结束；停止后的已核实同一会话保留显示，新账号或新进程不能串入旧值。

关闭界面保留已经运行的后台采集，需要结束时使用“停止采集”。再次打开界面会识别后台进程。GUI 启动日志和采集日志位于项目的数据与日志目录；`collector_status.json` 的旧 `running=true` 不能单独证明进程仍在，界面还核对进程身份及最近进展。

档案列表按当前快照展示每封战报，历史版本不重复计作多封。详情保留五组件状态、双方与武将、原始 ID、中文事件解释和未知值；原文导出继续使用归档模块的文件保护。查询在后台线程中以只读连接、有限时间与分页执行，避免为刷新界面遍历全部历史字段。

## 完整性含义

- **文件保存完整**：原文件字节与内嵌 BLOB 或经 `report_cloud_files` 引用读回的云端／缓存原文、SHA-256 一致；已迁移行的 `raw_bytes` 为空占位。full 索引全部节点，compact/lean 按保存策略建立索引，完整原文和事件仍可核对。
- **单封组件完整**：基础、详情、完整事件、统计、武将快照均取得，快照分页结束，无请求错误、序列化问题和待核实警告。
- **范围枚举完成**：本轮所选范围的根列表与所有已发现子列表到达末页。没有观察到战报时，只记录枚举结束，不能据此认为单封采集已验证。
- **本轮采集完成**：范围枚举结束，且发现的每封战报组件完整；不涵盖已过期、无权限或服务器不可访问的数据。

`legacy` 表示旧导出无法证明五个组件齐备；`partial` 表示存在缺失或警告；`complete` 表示单封组件检查通过。保存完整与服务器返回完整是不同结论。

终端提示描述本次保存的快照版本。`partial` 不限定为只有基础信息：例如已有事件、详情和统计，仅快照请求超时，仍会保持部分状态。各组件的具体缺失和错误可从 `report_components.status_json` 查询。不同版本保留，当前视图优先选择较完整的数据。

请求等待曾经超时，但实际导出时相应组件已经完整时，原超时转存 `requestHistory`，不再当作当前缺失；其他请求错误仍保守处理。实际导出仍缺组件、快照未结束分页、零事件或存在序列化问题时，继续保持 `partial`。

## 表结构

| 表或视图 | 内容 |
|---|---|
| `report_files` | 内嵌原始字节或已迁移空占位、原件 SHA-256 与长度、来源及解析状态 |
| `report_cloud_files` | 夸克对象位置、原文与 gzip 校验值、回读状态及错误；原文读取经统一接口校验 |
| `report_imports` | 导入尝试及错误 |
| `report_records` | 账号命名空间、战报 ID、当前较完整快照 |
| `report_snapshots` | 所有版本完整 JSON、完整度、问题、事件和节点数、保存模式及实际索引数 |
| `report_fields` | 策略选取的 JSON 节点 Pointer、父路径、顺序、类型和值；完整组件仍在原文中 |
| `report_components` | 五个组件及新增未知组件的完整原文和状态 |
| `report_events` | 从 0 开始的事件序号、eventId、tab 和完整原文 |
| `report_sides` | 双方原文及玩家、军队、阵型等查询字段 |
| `report_heroes` | 参战武将原文、站位、等级、兵力 |
| `report_skills` | 战法原文、ID、等级 |
| `report_current_*` | 当前较完整版本的查询视图，旧版本仍保留 |

缺失数据为 NULL，不填成零。ID 按文本保存；Lua 请求的战报数字 ID 超过精确整数范围时直接报错，不四舍五入。未知事件参数保留原值，不猜测伤害或治疗含义。

原始列表响应、分页游标、重试时间与运行状态还保存在采集目录的 JSON 文件中；数据库中的战报快照包含该战报的来源观察和组件状态，不能把整个运行状态文件视为数据库表。

## 中文语义辅助表

中文解释单独保存，不改写 `report_files` 的原字节与哈希，也不替换 `report_events.raw_json`、字段原值或战报组件完整度。

| 表或视图 | 内容 |
|---|---|
| `report_semantic_versions`、`report_semantic_settings` | 映射版本、字典及代码来源、当前使用的版本 |
| `report_semantic_runs` | 每个战报快照的语义处理状态、计数与错误 |
| `report_id_meanings` | JSON 路径、ID 类别、原值、中文名称、来源及未映射原因 |
| `report_event_meanings` | 事件序号、中文名称、中文摘要、逐位参数说明、状态及来源 |
| `report_current_id_meanings`、`report_current_event_meanings` | 当前较完整快照、当前映射版本且处理任务已完成的解释 |

`config/semantics.json` 指定 `data/dictionaries/` 下的 ID 字典、事件字典和客户端字典快照。导入与采集会尝试加载该配置，为成功归档的输入附加解释；旧快照可用 `enrich` 回填。映射版本包含来源与代码标识，新版本可以重新建立辅助数据，原始战报继续保留。

历史回填可以放在独立的 `enrich` 进程中与采集同时运行，本次采用了这一方式。回填从已保存的快照读取，不连接游戏、不发送补采请求；原文采集与历史解释分别记录进度，语义失败不回滚已提交的原文。桌面启动器打开图形界面，用户点击开始后才采集；独立回填进程并非每次启动时自动创建的功能。

事件参数保存 `position/key/label_zh/raw_value`，有依据时附加 ID 中文名、数值还原、单位和来源引用。`tab` 是日志嵌套缩进层级，不是回合号。定点数只按对应事件定义还原，原值不会被除法结果替换。当前客户端字典与历史源码的出处分别记录；同 ID 的场景冲突、未知配置、未知事件及多余参数明确保留，不猜测补值。

`schema_status` 表示事件参数结构是否识别，`id_mapping_status` 表示所需名称是否解析，两者保存在事件 `mapping_json` 中。所需 ID 名称未映射时，用户向的事件 `status` 为 `partial`，即使参数位置都已识别。`report_semantic_runs.status='ready'` 仅表示这次解释处理完成，不保证每项均已映射；语义状态也不改变战报的五组件完整度。

```powershell
# 仅处理当前较完整快照；省略 --current-only 则包括历史版本
python -B battle_reports.py enrich --current-only
# 限制回填批量；已有同版本结果默认复用
python -B battle_reports.py enrich --current-only --limit 10
# 查看一封战报，--limit 限制展示的事件数量
python -B battle_reports.py explain 10014231360057 --limit 20
# 同一ID存在于多个账号时，增加 --namespace 指定账号命名空间
```

`enrich --force` 重新计算所选快照的当前版本解释；`explain` 只读，不会触发补采，尚未生成解释时会提示先执行 `enrich`。`explain --out <输出文件>` 可输出解释，沿用已有不同内容文件不覆盖的保护。

## 查询

在项目目录运行 `python -B battle_reports.py query "SQL"`。查询入口只允许读取，拒绝附加数据库、导出数据库、修改表及写设置。

```sql
SELECT namespace,battle_uid,completeness,event_count,field_count
FROM report_current_snapshots;

SELECT pointer,node_type,value_json
FROM report_current_fields
WHERE battle_uid='10676989120025'
  AND pointer LIKE '/data/battleSettlement/attacker/army_member/0/%';

SELECT sequence,event_id,tab,raw_json
FROM report_current_events
WHERE battle_uid='10676989120025'
ORDER BY sequence;

SELECT battle_uid,hero_uid,position,level,troops_initial,
       troops_remaining,troops_dead,troops_wounded
FROM report_current_heroes;

SELECT s.id,s.completeness,s.event_count,s.issues_json
FROM report_snapshots s JOIN report_records r ON r.id=s.report_id
WHERE r.battle_uid='10676989120025' ORDER BY s.id;

SELECT source_path,sha256,error,byte_count
FROM report_files WHERE parse_status='failed';

SELECT battle_uid,kind,raw_value_json,name_zh,mapped,status
FROM report_current_id_meanings
WHERE battle_uid='10014231360057';

SELECT sequence,event_id,event_name_zh,summary_zh,parameters_json,status
FROM report_current_event_meanings
WHERE battle_uid='10014231360057'
ORDER BY sequence;
```

查询结果默认最多显示 100 行，增加 `--limit` 可调整。每封原文件可以用 `export <快照ID> <输出路径>` 原样导出。

## 恢复和重试

文件先原子保存，再提交数据库，最后记录完成。入库失败保留待导入版本；重启扫描账号目录中的版本和最新文件，恢复文件已落盘而数据库未提交的中断。重复文件按内容哈希跳过。损坏输入保留原字节和错误，不阻断其他正常文件。

只有统计或武将快照返回、尚无基础／详情／事件时，也保存为部分版本，`source` 标明实际来源，全部原文和递归字段照常入库。明确返回的 `false`、0、空数组继续保留；基础／统计组件若是标量，不能算完整。没有任何组件时仍报告 `not_found`，并在续采状态中保留实际请求及响应审计。不同错误和缺失不会覆盖数据库中原有较完整版本。

列表发现新战报或变化信息时，立即保存 `captureKind=list_discovery` 的基础快照并入库，不必等待所有列表和详情请求结束。这种快照明确标记为部分数据，保留未知字段和来源观察，不改变列表覆盖或组件完成状态；失败导入保留原文件并重试。已有完整快照不会被基础快照覆盖。客户端数字账号标识与历史字符串标识比较前统一为十进制字符串，避免恢复时误判账号冲突。

采集调度以补齐为优先：先恢复已落盘待入库版本，并处理一小批已有待补记录；缺少组件较少的记录排在前面。每收到一页根列表或子列表，先保存该页和发现信息，随即获取该页战报的五组件，再继续下一页。本轮已尝试的记录不在同轮反复请求，失败仍按退避时间安排后续重试，不能通过频繁更新列表信息清除组件失败退避。

每轮从第 1 页重新枚举根列表和子列表，已保存的战报内容与待入库状态继续复用；失败页码只用于诊断，不按可能漂移的旧位置跳过中间页。后续根页失败也继续处理已经发现的子战报。完整战报后来新增的列表信息或范围关系，会重新归档，组件可以复用已有数据。

内容完全相同的列表响应复用同一原文文件，字段变化时保留新版本。历史文件的完整恢复扫描在启动、首次进入账号和入库故障后进行，正常轮询不重复扫描所有历史文件。一个损坏账号绑定或文件不会阻止其他账号的恢复；身份冲突的文件保留并报错，不归入错误账号。

`collector_state.json` 检查点使用 compact JSON，只移除不影响 JSON 值的缩进和空白，不删字段、不改数字或类型、不改数组顺序。关键持久化边界仍包括页面确认、原文落盘后待入库状态、失败与结束；同一操作中重复的整份状态写入减少。原文仍先保存并刷新到磁盘，再提交数据库。Windows 短暂共享冲突继续有有限重试，永久失败仍会报错并保留原目标与临时内容。

保存阶段的 `atomic_json` 使用原来的JSON格式参数一次编码，通过 `atomic_bytes` 完整写入临时文件并flush/fsync，然后原子替换。已经编码并计算SHA的发现版本、缓存重试检查点、正式历史版本直接复用同一字节，避免再次序列化。历史版本与最新别名仍分别写入确认；替换失败保留旧文件与完整临时文件。编码失败在新临时文件创建前返回，不破坏已有恢复文件。

字段索引只优化与旧标准库输出等价的标量编码：原生整数复用十进制文本，布尔复用true/false，浮点只生成一次标准JSON文本，原生字符串使用同一标准库ASCII编码器。代理字符、非ASCII标量、数值子类、无效值异常及路径转义继续保留原行为。未修改表结构、SQL事务、完整度门槛、分片覆盖、请求等待或中文语义版本。显式一批战报在排序前过滤，不改变其原优先级、稳定顺序和恢复规则。

核验和状态读取使用只读数据库连接；核验固定同一个 SQLite 读快照，避免并发写入造成前后计数不一致。导出和核验结果禁止写到数据库本体、sidecar、硬链接或已有不同内容的文件，防止误覆盖原始数据。

角色、服务器、场景和客户端对象改变时，当前请求会失败，避免混入另一个账号的数据。主入口同时只允许一个采集器使用同一数据库。维护、未登录或进程关闭时，持续模式记录错误并等待下一轮；单轮模式返回非零。Ctrl+C 停止，已提交数据保留。

Lua 桥接失效与服务器组件等待超时分别处理。已取消的 Lua 排队任务、已销毁的脚本或明确的传输错误触发 `RuntimeBridgeUnavailable`，当前会话后续执行立即失败，采集器结束本轮并由持续模式重新连接；不会继续对整个账号逐封等待。原文、待导入文件和重试状态继续保留。同一持锁采集进程跨轮复用自己的监听 owner，避免清理尚未执行时被自己的旧租约阻塞，不接管其他 owner。

`collector_status.json` 在每页、每封开始、入库和失败时更新 `last_progress_at`、当前战报及错误等信息，窗口同时显示具体失败原因；`collector_diagnostics.jsonl` 持久保存事件。进程存在或 `running=true` 只表示持续任务尚未退出，应结合阶段和最近进度判断是否推进。Windows 多进程自动选择优先唯一可见游戏主窗口；不能可靠确定时要求通过 `--pid` 或启动器 `-GamePid` 指定，不关闭其他实例。

零事件原样保存并标记待核实。客户端存在缓存直接返回的行为；缺失组件请求现在会按真实发包及对应战报的响应核对，区分“方法已调用”和“已实际发包”。对仍在有效期内的残缺快照缓存，先将原缓存完整落盘，等待客户端自己的有效期自然结束后，最多再调用一次原请求；不直接清缓存，不改写游戏数据。重试前后的原文分别入库，入库中断先恢复这些文件，再发新请求；不保证恢复服务器已经清理的数据。

快照分片按本次响应的页码及分片覆盖核对；重复页不延长等待。实际收到新页时可以继续等待，20秒无进展或60秒总上限结束；有明确错误、缺页或序列化问题仍保留为待补齐。根列表暂时失败时，已保存的未完成连战组可以独立、有限重试，不把历史恢复伪装成本轮可见列表已全部覆盖。

残缺快照及 `_allCombatSlices/_detailCombatSlices` 在原客户端方法可能清理缓存之前先原子保存；重发前再保存等待期间的新增页。尚未拼合的片段在 `componentFragments` 下按原值、二进制与Lua键类型归档，即使最终请求未获得正文，已保存检查点也会在当轮导入。仅检查点的中断状态用 `pendingImport.path=null`，恢复时先按SHA导入这些文件，原失败结果仍为失败，不虚报完成。

`__codexBattleReportRetained` 是独立于短时观察器的原文暂存队列。实际调用原RPC前冻结当前残缺缓存；每个目标响应在原处理器执行前冻结完整proto，防止节流期间新增页被清理，以及错误响应清缓存/原处理器就地改写。保留的是独立序列化字符串，非客户端table引用。`cache_fragments/response_fragments` 载体始终为部分版本，`responseFragments` 保存原proto，不替代完整事件或快照正文。状态轮询只读取数量，正文在导出及原子拆钩子时集中读取，按SHA原子落盘后才按ticket确认清除。账号、服务器、赛季及战报ID共同限制读取与确认；全缓存路径也恢复匹配的旧暂存。观察器关闭和重新安装均不删除未确认正文。桥接或写盘失败保留队列供同一游戏进程后续恢复，已落盘文件由正常恢复扫描处理；尚未落盘的内存内容不保证在游戏退出后恢复。

短时压制识别分别读取all、detail和snapshots的实际缓存及有效期，只有确认未实际发包且有效期结束后才有限重发。响应审计保留全部旧行，并按当前实际发送代核对覆盖；该发送代表示收到时的本地发送计数，不宣称协议没有请求标识时也能识别所有晚到旧包。已经置完成标记但解码结果不是表的快照，会保存原文并在确认无实际发包时立即报 `client_cached_incomplete_component`，而非继续无效等待；不手动清理游戏缓存。

每轮优先发现当前列表，删除首次读列表之前的旧网络补采批次；本地恢复仍由启动扫描、页内及轮末处理。旧网络重试的启动预算为页内约 `wait_seconds`、轮末约 `4*wait_seconds`（默认约20秒及80秒）；预算结束后不再启动该批下一封旧尝试。当前已开始的单封仍保留完整网络等待，首次发现、本地待入库及完整元数据刷新继续执行。旧重试先按attempts、lastAttemptAt轮转，再比较缺失组件数，防止异构积压中多缺项记录长期得不到机会。延后不会增加attempts、清除nextRetryAt、永久跳过或改变完整度，摘要的 `deferredRetries` 记录实际仍待后轮重试的ID。

预算按旧网络采集分支的实际处理时间扣除，新报、完整元数据刷新和纯本地恢复不消耗旧报额度；0额度继续禁止旧网络尝试。有限额度时并行预取不将旧报夹在新报组中，已经inflight的请求仍完整收尾。

root/child请求之前不再额外保存仅用于重建的游标；实际收到响应后的原文、pending及页后游标确认边界保留。最后一个child页在页后必要保存前同步child/group完成标志，因此不再紧接着重复保存整份状态；失败、停止及保存失败仍走独立错误保存。不能用此优化省略任何子页或在原文持久化前推进游标。

`pendingImport` 的全量原文路径在首次导入前持久化。`_replay_pending_capture` 的每个检查点提交后不再单独调用整份 `save()`；本封完成或失败时保存结果。中途终止可从旧完整队列重放，已提交项按SHA返回duplicate，未提交项继续，保留原文、字段索引及语义处理。不能在首次pending清单落盘前开始导入。

统计响应的 `binStatics` 缺失或少于4字节时，原客户端立即返回而不建立统计缓存。观察器保留原值和长度原因；仅当同战报、当前实际发送代匹配时，覆盖核验返回 `server_empty_component`，立即结束该组件无效等待，仍标为部分数据。ID为0或缺失ID的错误提示只记notice，不据此猜测目标请求。

显式ID补采入口同样先导入 `cacheCheckpointPaths`，无论最终 `exported` 是否为真；去重后再导入最终文件。失败结果保持失败，部分正文在当轮即可查询，相同SHA重放不增加历史版本。

`lua_hook` 原生执行异常及Frida原生访问错误属于 `RuntimeBridgeUnavailable`，结束当前连接的组件/战报队列，持续入口保留检查点并在后续轮次重连。正常Lua业务错误与服务器组件超时不因此被升级为桥接故障。首次原生访问异常的触发根因未完成实机定位，不能将错误分类与停止级联的修复当作首次异常已根治的证明。

连接错误中的原始 `result` 会作为 `runtime_error` 写入状态和 `cycle_failed` 诊断，保留nativeOperation、rawL与threadId等实际提供的字段，避免只剩错误字符串而无法定位发生在哪个原生调用。

## 每日分类、武勋与最近一天对手

`battle_ui/daily.py` 从当前最佳版本和双方结算表只读统计。日期优先使用战斗结束时间，缺失时使用战斗开始时间，并换算为北京时间；无有效战斗时间的记录单独计数，不拿入库日期代替。个人／同盟／收藏来源可能重叠，因此来源列不相加为总数。

武勋只使用实际结算的 `zgNum`。`originZgNum` 是结算前相关值，`barbarianPoint` 是其他积分，均不替代武勋。明确的零记为0，缺失字段记为未知。按账号范围和玩家ID聚合，排除系统部队；已知连战父级汇总不与其子战报重复计入。未齐连战组、未知父子关系、缺武勋字段及部分组件记录继续显示覆盖提示，不能把档案内的已知合计称为账号完整总武勋。

`battle_ui/opponents.py` 仅保留最近有战报的一个北京时间自然日的名单视图。先通过角色本人所在侧判断另一侧；本人不参战时，只在同日己方同盟唯一、且能唯一确定己方侧时判断。无法确认者单独统计，NPC排除。高品为任一武将进阶≥3，单将满红为5阶，整队满红要求三名不同且已识别的武将均为5阶。缺进阶保持未知。按玩家ID合并人员、按真实武将排列区分队伍，相同队伍保留当天最近一次观察，保留来源战报及快照ID。此限制只作用于名单展示和导出，不删除历史原文或快照。

GUI的“每日统计”“对手名单”在后台读取上述统计，切换账号时立即清除旧账号的显示和导出缓存。统计CSV带UTF-8 BOM，保留0和空值区别，并保护数据库及其附属文件，拒绝覆盖已有文件。

## 按次无双记录

`battle_ui/peerless.py` 仅读取当前战报快照中的连战汇总与客户端判定。原始汇总来自根列表 `BlockBattleReportInfo.otherInfo.continuousInfo`，采集时保存在 `/discovery/<n>/row/otherInfo/continuousInfo`；客户端附加到战报缓存的同字段也会检查。子列表只有单场 `CombatInfo`，不会因此继承父连战的无双。

分页原响应旁的 `clientPeerlessEvaluations` 由 `capture/game_assets/peerless_capture.py` 在既有响应读取中计算，不改网络 row 或 response，也不新发请求、不加载额外游戏模块。只在已加载的当前 `BattleReportHelper.IsLegend` 可用、输入有效且属于常规多场连战时调用实际判定函数；使用 `combatInfo.endTimeStampTime`，不拿入库日或今天代替。原页保留判定函数字节码；各观察的 `clientPeerless` 保存函数 SHA、实时枚举与阈值、原始输入和严格布尔结果。蛮族 PVE 传奇、缺函数、缺时间及异常值明确分类。

读取端核对判定的战报ID、达成人员ID、汇总武勋、获胜场数、类型、时间与该观察原文一致后才确认。历史本地配置曾为20000武勋及5胜，但此页面不将历史值当作当前规则自行推算。账号运行身份冲突或相同输入下真假判定冲突均不确认；同组从早期未达成发展到后来达成属于正常进度。缺少依据的空名单不能解释为账号无人打出过无双。

记录按 `(namespace, blockHash, continuousInfo.avatarId)` 去重，没有连战块时明确回退到战报ID。同人不同连战分别计次；多来源的证据和实际快照指针全部保留，记录只关联那次连战及该人资料。详情跳转仅查询对应来源快照，不查询该玩家其他历史战报。全部日期可筛选，CSV仅导出当前无双事件；原始数据库继续归档，不重复复制完整战报或删除历史。

## 有限预取与等待预算

当前代码与启动器保持默认窗口为 1。窗口 2 的冷缓存双封实机复测未通过，出现组件超时，因此 `--parallel 2` 至 `4` 仅保留为实验手动参数，当前应保持默认值 1。存在参数、节流逻辑或离线模拟通过，均不能当作网络并发实机完整验收成功，也不能据此声称账号所有战报已采齐。

窗口 2 的实验方案只跨封预取缺失的 `all/statics`，`snapshots` 不预发，在逐封处理时才请求并等待该封导出后再处理下一封。所有 Lua 调用仍在同一个游戏线程顺序执行，没有 Python 线程同时操作 Lua。实验预取和延后的正常缺失请求共享同一 runner 的节流记录，同方法及任意新请求间隔均至少为 `max(1秒, request_delay)`，跨批次继续生效；缓存命中不计作发送。

默认每个实际请求仍有发送后的 20 秒网络等待预算。节流等待不扣除这个预算；已经预发的请求只等原 deadline 剩余时间，不重复请求，也不在原期限结束后重新增加 20 秒。停止时对已预取但未处理的记录只导出当前缓存，不发新请求、不额外等待，数据仍按原完整度门槛检查。快照缺页或服务端限频保留为失败原因，不当作完整数据。

## 测试与实机验收

公开副本的离线回归位于 `tests/`，测试临时文件写入项目的 `.runtime/`。需要真实战报样本或原始反编译 Lua 的历史集成用例会在缺少样本时跳过；这些外部样本及原项目的根目录端到端入口不随仓库分发。默认 pytest 仅收集 `tests/`，不触碰正式战报或数据库。

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
$env:TEMP=(Join-Path (Get-Location) '.runtime/temp')
$env:TMP=$env:TEMP
# 本次使用的可选 Lua 5.1 测试运行时；不影响生产采集依赖
# Optional Lua tests use the pip-installable lupa package.
python -B -m pytest tests -q -p no:cacheprovider --basetemp=.runtime/pytest
python -B battle_reports.py verify
```

已在登录后的真实客户端验证列表、子战报、单封五组件及入库，采集期间也观察过连接、分页超时和服务端限频。中文解释有独立的字典、事件参数、原文保护及重建测试。实时数量与当前进度以 `status` 和最近的验收记录为准，不能由局部成功推断账号全量完成。

运行 `start_battle_archive.ps1 -Once`，继续验收三个范围及子战报的连续分页、逐封五组件、游戏界面样本与数据库对应关系、重复运行和中断恢复。单独请求某个偏移的空响应不作为整份列表结束证据。列表原响应在客户端处理前保留，客户端回调异常和服务端拒绝分别报错；启动连接及脚本加载默认总预算 15 秒，关闭脚本和分离会话各 5 秒，超时后持续模式按轮次重试。
